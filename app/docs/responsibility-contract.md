# 星账职责契约：用户、表层交互、底层系统

版本：R1，2026-10-03（北京时间）。依据用户本轮要求，先确定职责，再修改功能。本文件定义目标责任，不表示这些能力已经实现。实际状态与执行顺序唯一入口：[M1–M7 执行计划](m1-m7-execution-plan.md)。

维护范围为 `app/` 单人版。保留 M1–M4 已确认方向，不把 `legacy-duo/` 的双人功能带入当前范围。手机侧重快速记录、拍照/分享与轻量纠错；电脑侧重批量导入、整理和对账。两端调用同一业务契约，不能产生两套账务语义。

## 1. 三层职责，五个系统责任主体

| 主体 | 必须负责 | 不应负责 |
| --- | --- | --- |
| 用户 | 提供本人知道的真实信息；表达消费用途和偏好；在证据确有歧义时选择；决定删除、恢复、校准等会改变结果的动作 | 选择内部事件码、核对状态、分录符号；维护来源身份、提交顺序、退款关联生命周期；重复确认确定事实；诊断技术失败 |
| 表层交互 | 组织“记一笔、导入、修改、查看消费、核对账户”；收集最少输入；保护草稿和选择范围；展示结果、差异、待回答问题及撤销入口 | 直接写资金变化/消费影响；自己解释渠道、负债符号、退款归属；自行选择冲突赢家；把内部队列改名后继续交给用户管理 |
| 应用服务 | 编排完整任务：读取最新快照、验证请求、解释/解析、去重、生成原子计划、执行、返回可呈现结果；维护重试和问题生命周期 | 把编排拆成用户必须依次点的技术按钮；在多个页面复制规则 |
| 领域与账务核心 | 交易语义、不变量、金额整数分、资金方向、消费影响、退款限额与关系有效性；生成合法账务命令 | 认识弹窗、按钮、设备文件路径；靠显示文字或分类名称猜账务 |
| 查询层 | 从有效事实生成账户流水、余额、消费贡献与下钻 IDs；报告缺失基线和冲突 | 另写一套统计口径；把未知当零；用展示金额代替消费影响 |
| 存储与同步适配 | 原子持久化、历史、幂等、迁移、备份、加密同步、恢复和冲突候选保存 | 改变业务含义；按设备时钟替用户决定财务冲突；让用户修复部分写入 |

“系统能知道”必须有证据：结构化事实与确定规则 → 适用且未冲突的稳定记忆 → 上下文候选 → 必要时问用户。AI/OCR 只能提供解释或候选，不能覆盖明确来源或用户修改。**少问不是猜测；隐藏机制不等于隐藏实际问题。**

## 4. 必须明确的六条实现契约

这些是目标约束；M5.0-B 只核对现有代码和具体缺口，不扩建通用框架。任一实现与下列约束冲突，先更新决策记录并说明原因，不能把现有行为当需求。

- **C01 字段权威**：原始来源永不改写。用户改过的金额/账户/时间/性质/分类/名称/备注，不被重导或规则静默覆盖。来源确定字段与分类建议分开；实质财务变化展示字段差异；无财务含义的文本变化只附证据。现有整笔来源选择不等于此契约完成。
- **C02 身份与证据**：一个 namespaced 来源身份对应最多一笔有效经济记录，可保留多份不同版本的不可变证据；一笔交易可有多个来源；一份证据只属于一笔交易。相同证据重复幂等；弱匹配不强并。这修订 M4“一个身份最多一个稳定 SourceRecord evidence identity”的歧义，必须在 #6 核对现有版本表达及迁移。
- **C03 状态与问题**：已知 PENDING 不产生实际资金/消费，后续成功只结算一次；FAILED 来源不占用已提交交易身份。未知账户/关系仅影响该部分，金额/日期等核心事实不明才暂缓该条。一次回答与必要账务更新、记忆、结果保存必须一致，重试不吞问题。
- **C04 修改与关系**：用户提交的是字段意图，应用层用当前快照补全；不可用旧表单覆盖未编辑字段。金额/账户/消费/关系同一原子任务，失败全回滚；关联无效保留交易事实并产生可处理的问题。技术故障不能被当作普通关系歧义吞掉。
- **C05 记忆与恢复**：记忆限定平台/profile/渠道等适用范围，失效或冲突则停用；仅改本笔不自动改未来规则。软删除重导默认不复活，恢复必须显式；恢复保留用户修改。彻底删除沿现有告知契约单列。批次撤销必须区别新增与复用，不能删掉先前账单。
- **C06 派生与持久化**：余额和消费分开、来源与修改历史分开；未知余额≠0；输入实际余额先比较；已知未决冲突按现有规则阻止合计。Web 与 SQLite 的事务/恢复分别验证。读写采用最新快照校验，界面只消费应用返回结果。

| 旧机制 | 处置 | 替代方式 / 删除条件 |

## 6. 后续每项开发的固定检查清单

1. 引用 R 编号、C 契约和 M 节点，写明减少哪项用户负担。
2. 列出正常路径的用户步骤；每一个额外问题写明缺少什么证据、为何不能自动处理。
3. 指定应用服务、核心不变量、持久化对象、查询输出；不能把业务编排放回 main.ts。
4. 写明取消、刷新、失败、并发、重试、删除/恢复、后续修改会发生什么。
5. 明确旧入口保留/迁移/移除及对应回归；不因删旧测试就宣称新流程完成。
6. 用账务一致性测试和真实用户路径共同验收；提交/CI/部署/用户验收分别记录。

用户体验不是“按钮少”一个指标。还要看是否少重复输入、少内部概念、误操作可恢复、范围可见、未知信息不伪造、结果可解释。不能用自动猜测换取表面上的一步完成。
