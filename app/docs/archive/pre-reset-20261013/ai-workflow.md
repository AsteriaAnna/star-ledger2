# AI 开发入口与验收规则

本文件供复杂合并、清理及跨入口任务按需参考，不要求每次任务通读。产品约束见 [方向](../../product/direction.md)；事实状态见 [当前状态](project-status.md)；唯一执行顺序见 [M1–M7 计划](m1-m7-execution-plan.md)。历史日期报告按需检索，不作为默认必读清单。

## 开始

1. 核对当前分支、HEAD、未提交修改、远端 PR 和相关部署状态。不同环境的“本地提交”必须用可读取的 SHA 验证，不能代替远端事实。
2. 用一句话写清用户任务和可观察的完成结果；定位实际入口、调用链及已有测试。按相关文件搜索，不通读全部历史文档。
3. 明确本次修改边界：截图识别、业务入账、同步、UI 等可分离的任务分别提交。已有代码保留其已验证语义。

## 实施和判断

- 一次完成一个可验收任务。涉及账务时检验 Transaction、BalanceMovement、ConsumptionEffect 的关联及余额/消费口径；不得通过 UI 直接改余额。
- 先判断测试是否覆盖当前入口、是否模拟云端，以及有没有财务断言。不能以“全部测试绿”代替真实截图、浏览器、云端或真机证据。
- 相关改动运行相应测试、类型/构建；用户交互检查保存、刷新、修改/撤销、同步后的结果。未部署的代码只报告代码状态。
- 对非阻塞旁支留下具体问题，不扩大成全仓重构。失败时在任务范围内修复并复验；通过后停止重复检查。
- 成果写明提交、改动文件、运行的命令或操作、结果和未覆盖环境。不能用完成百分比代替证据。

## 删除、合并和重构

- 文档：保留可追溯证据，解除旧计划的“当前入口”地位；不建立第二份路线。明确替代后才移除失效入口。
- 代码：先查静态/动态引用、构建、发布配置和功能替代路径；保留有价值的账务测试，只更新过时交互断言。
- PR：对照 main 的完整差异、CI、真实功能门槛和部署边界。草稿、超出题目的大规模删除或未验收云闭环不能整包合并；可从中提取独立小改动。
- 分支：先确认已合入或成果有替代且没有独有工作，再清理远端。名称旧或数量多不是删除理由。
- 结构：目前 domain/accounting/application/storage/sync/web 已形成；局部职责问题随具体功能处理，不先整体搬迁。
