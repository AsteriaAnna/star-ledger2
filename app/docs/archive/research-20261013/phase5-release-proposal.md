## 一、当前产品状态盘点

沿用已确认的 `main@63ab2e2` 事实。表中的体验来自代码路径分析，**尚未完成真实浏览器、真机和云端验收的部分不能写成“已经可用”**。

- **代码存在**：找到实际实现。
- **功能可用**：在目标环境中验证成功。
- **闭环完成**：正常操作、失败重试、重新打开后都能继续完成任务。

## 二、V1 发布目标

### V1 的使用范围

首个版本服务于**单人、人民币、微信与支付宝为主要来源**的日常记账。用户可以在手机和电脑浏览器中访问，同一账户查看已同步账务。

“受邀发布”只是限制开放范围，不降低数据正确性和恢复要求。

### V1 必须包含

| 功能           | 冻结到什么程度                                    | 必须包含的原因                    |
| ------------ | ------------------------------------------ | -------------------------- |
| 开始使用与账户管理    | 可建立资金账户；未知余额明确显示；导入时可直接创建或绑定账户             | 用户不能为了导入先完成一套技术配置          |
| 日常记账与账单管理    | 手动记录、修改、删除、恢复；覆盖消费、收入、转账、还款、退款等已支持主要场景     | 构成日常持续使用的基础                |
| 微信 / 支付宝文件导入 | 正常记录自动处理；重复不重复入账；每条有效记录有明确结果；少量异常可处理或跳过    | 批量导入是现有项目的核心价值             |
| 截图辅助记账       | 支持常见微信 / 支付宝详情截图、多图选择、逐张结果及重试；识别不完整时能补充后保存 | 手机端不能依赖电脑导入，也不能要求用户反复打开选择器 |
| 统计与余额        | 期间消费、退款、净消费、分类和账户余额；随编辑、删除和恢复一致更新          | 用户需要看到记账后的实际收益             |
| 受邀账户与同步      | 受邀用户可开通、登录，同一账户跨设备同步；离线保存、联网续传             | 满足手机与电脑共同使用                |
| 数据恢复与状态说明    | JSON 备份恢复、受保护的恢复凭据导入；明确区分本机已保存和云端已同步       | 长期使用不能依赖单一浏览器数据            |
| 面向用户的异常处理    | 导入、识别、保存和同步失败后都有明确下一步                      | 防止用户卡在系统内部状态中              |

截图的发布承诺应是\*\*“辅助录入，保存前核对”\*\*，不承诺所有版式、所有字段都自动识别，也不承诺后台静默记账。

### V1 暂缓

| 暂缓项目                                      | 原因                                  |
| ----------------------------------------- | ----------------------------------- |
| 双人空间、关系绑定、共同分析与消息                         | 涉及权限、数据归属和共享解密，超出单人闭环               |
| Android / iOS / Windows 安装版、系统分享入口、后台截图捕获 | 涉及平台生命周期及权限；先稳定网页版的交易生成能力           |
| 微信登录、短信验证码及公开自助注册                         | 引入更多身份和密钥恢复场景；首版采用受邀账户              |
| AI 自动分类、视觉模型自动决定账务性质                      | 当前首要问题是已有输入能否可靠入账；AI 结果仍需独立的确认与追溯边界 |
| 多币种、预算体系扩展、复杂资产管理                         | 不影响当前用户完成基本记账                       |
| 全部未完成草稿跨设备同步                              | 增加状态同步范围；V1 先保证正式账务同步，并明确草稿留在本机     |
| 原图片和原账单文件长期云端归档                           | 会增加存储、隐私与删除责任；首版明确保存哪些提取证据          |

## 三、功能开发路线

以下是有依赖关系的开发包。每个开发包交付可体验结果，**不另开一轮全面审查**。

### 1. 基础记账与修改结果一致

**用户问题：** 用户修改一笔金额、删除消费或恢复退款后，账单、余额和统计必须一起正确变化。

**当前实现：** 已有业务命令、编辑规划器和生命周期处理。

**发布缺口：** 需要把这些路径在实际 Web 入口中验收，并修复验收中出现的具体问题；不能把底层约束不足直接扩大成全模型重构。

**技术影响范围：**

- Web 记账表单、详情、回收站与保存路径。
- `accounting/business`、交易编辑及生命周期 application。
- Transaction、BalanceMovement、ConsumptionEffect、关联退款和 Operation。

**顺序：第一个。** 后续文件和截图最终都要生成、修改这些账务。

**用户验收：**

- 记一笔消费后，账单、消费统计和对应账户变化一致。
- 修改金额或付款账户，旧影响被正确撤销，新影响出现。
- 亲情卡消费增加本人消费，不扣本人账户余额。
- 删除后退出统计，恢复后正确回到统计。
- 有关联退款时，修改、删除和恢复不会制造重复退款或超额冲减。
- 刷新页面后，已保存结果仍然存在。

### 2. 文件导入完成闭环

**用户问题：** 用户希望“选文件后基本完成”，只处理确实无法自动判断的少数记录。

**当前实现：** 已有批次、解析、去重、账户解析、提交结果和部分问题处理。

**发布缺口：** 每条记录的去向、阻塞问题的处理入口、失败后继续、完成提示与清理范围。

**技术影响范围：**

- 文件选择、`importer`、`import-v2-flow` 和导入结果界面。
- importing、导入 application、账户记忆及退款处理。
- ImportSession、ExternalRecord、Attention、Outcome，以及正式账务实体。

**顺序：第二个。** 文件字段相对明确，先建立可信的批量入账行为，也为截图提供可对照的账务结果。

**用户验收：**

- 导入支持格式的微信或支付宝账单，正常记录直接进入账单。
- 不要求用户预先建立所有资金账户；必要时可在导入过程中创建或绑定。
- 再导入同一文件，不重复增加消费。
- 显示新增、重复、无需入账、待补充或失败数量，能够对应被识别为交易的记录。
- 无法解析的交易不能无提示消失；明确说明无法处理的位置或原因。
- 所有待处理项都能完成、明确跳过或重试，不出现只有“待确认”却无操作的死路。
- 关闭后重新打开，可以继续处理已保存的导入任务。

### 3. 手机截图记账

**用户问题：** 用户在手机上选几张支付截图，希望快速变成账单，不想反复选择图片、重复填字段。

**当前实现：** 单张本地 OCR、解析、核对、草稿和保存已经存在。

**发布缺口：** 多图选择、真实样例识别、逐张状态、失败重试，以及无法自动解析的资金信息如何补充。

**技术影响范围：**

- 图片选择、OCR 适配、截图解析、核对表单和 `captured-record`。
- 来源识别、重复判断与正式记账路径。
- 截图草稿、SourceRecord 和账务实体。

**顺序：第三个。** 先复用已经验收的账务行为，避免把 OCR 问题和账务问题混在一起。

**技术选择原则：** 本阶段不预定“更换 OCR 就能解决”。用获准使用的代表性截图，区分文字识别错误、字段解析错误和记账规则错误，再决定是否替换识别服务。

**用户验收：**

- 一次选择多张图片，能分别看到处理结果；一张失败不阻止其他图片。
- 常见支付、退款和亲情卡截图能进入可核对表单。
- 金额、时间、交易性质或付款方式不确定时可以补充，不能静默采用错误值。
- 保存后进入账单、统计及待同步范围；重复操作不会重复入账。
- 中途退出后，已保存的识别结果及用户补充内容可以继续处理。
- 如果不保存原图片，界面明确说明；需重新识别时清楚提示重新选择图片。

### 4. 统计与账单相互核对

**用户问题：** 用户需要知道“这个月花了多少、退款算在哪里、账户余额为何如此”。

**当前实现：** 已有期间统计、分类、趋势、余额和大额账单。

**发布缺口：** 页面间一致性、退款期间说明，以及未知或冲突状态的清楚表达。

**技术影响范围：**

- 概览、账单筛选、分析、账户页面。
- analytics 与页面现有聚合调用。
- 读取正式账务投影；不新增一套统计事实数据。

**顺序：第四个。** 用前面手动、文件和截图产生的账务，核对用户最终看到的结果。

**用户验收：**

- 同一期间的消费、退款和净消费可以相互核对。
- 修改、删除和恢复账单后，各页面一起更新。
- 退款按明确的发生期间展示。
- 未设置期初余额时显示“余额未知”，不显示具有误导性的零余额。
- 已知有未完成导入或账务冲突时，不把受影响结果展示为完整可靠的统计。

### 5. 受邀账户、跨设备同步与恢复

**用户问题：** 用户在手机记账后，电脑能看到；换设备或清理浏览器后，能够找回数据。

**当前实现：** main 有登录、密码包装密钥、同步和 JSON 恢复；注册在其他分支。

**发布缺口：** 注册能力安全接入、实际云端适配、访客账本处理、同步失败恢复、凭据导入和冲突处理。

**技术影响范围：**

- 登录、账本选择、同步状态与恢复页面。
- CloudBase 认证 / 云函数、platform 加密、sync、Web store。
- 用户与账本归属、密钥、Operation 批次、pending 和冲突；未完成草稿暂不纳入云同步。

**顺序：第五个。** 先让本地生成可靠账务，再验收这些账务的跨设备传播。已有分支成果可逐项复用，不能整包合并污染主线。

**用户验收：**

- 受邀用户能完成开通、登录和首次同步。
- 登录前有本地账单时，明确提示如何保留或带入账户账本，不静默切换成看似空账本。
- 手机新增或修改后，电脑同步得到相同结果。
- 离线记账后联网可继续上传，不丢失、不重复。
- 两台设备同时修改同一账单时，不静默覆盖；用户能完成受支持的冲突处理。
- 新设备可通过同一账户恢复已同步账务。
- 导出的 JSON 能在空本地账本中恢复；恢复凭据具有可用的导入流程。
- 区分“身份登录失败”“密钥无法解锁”和“同步未完成”，不能一律提示账单已同步。

### 6. V1 发布交付

**用户问题：** 用户需要一个明确、可访问、可持续使用的版本，而非多个入口和不清楚的测试地址。

**当前实现：** 有 Web 构建、OCR 资源和更新相关代码；当前实际部署状态不在本次已验证事实内。

**发布缺口：** 固定发布版本、唯一产品入口、目标设备验收和最短使用说明。

**技术影响范围：** Web 构建及静态资源、部署配置、版本标识、已有使用帮助。无需为此调整账务架构。

**顺序：最后一个。**

**用户验收：**

- 从统一地址进入，手机、电脑均可完成主要任务。
- 实际访问版本能对应到确定提交。
- 更新后原有账本仍可打开；资源加载失败不会误导用户认为账本丢失。
- 用户能找到备份、恢复、同步状态及反馈入口。
- 使用说明准确列出支持的文件、截图范围和已知限制。
- 完成一次真实连续使用验收，而不仅是逐按钮测试。
