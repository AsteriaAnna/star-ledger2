### 1. 产品定位：先把自己的钱记清楚，再看懂两个人的钱

建议将产品定位冻结为：

> **星账是一款面向个人及伴侣的轻量记账工具，通过截图辅助与自动化录入，帮助用户记录真实收支，并看清“钱在哪里、属于谁、由谁保管”。**

长期围绕三层能力发展：

| 层次     | 用户需要解决的问题                 | 产品承担的责任                    |
| ------ | ------------------------- | -------------------------- |
| 个人账本   | 我花了多少，还有多少钱？              | 保持交易、消费统计和账户余额一致           |
| 自动截图记账 | 能不能少填一点，截图之后就基本完成？        | 识别、补全、去重、入账，并让少量不确定情况容易处理  |
| 关系资产透明 | 我的钱有多少放在对象那里？对象的钱有多少在我这里？ | 分开表达账户持有人、资金归属和查看权限，避免重复计算 |

**情侣是首个重点使用场景，关系透明是建立在个人账本之上的能力。** 即使没有绑定对象，或者以后解除绑定，个人账本也应继续完整可用。

首页可以因绑定状态而变化，但底层不能因此换成另一套记账规则。

### 2. 用户画像：为实际使用方式设计

首批核心用户就是你们这样的组合：各自有银行卡、微信和支付宝，各自消费，也有互相代管的钱；手机用于快速记录，电脑用于批量导入和核对。

| 用户          | 典型行为                 | 最在意的结果                |
| ----------- | -------------------- | --------------------- |
| 希望轻量记账的个人   | 不愿逐项填写，愿意上传支付截图      | 操作少，账单能留下来，错了容易改      |
| 愿意相互公开账务的伴侣 | 保留各自账户，希望查看对象近期交易和账户 | 能看懂双方情况，不需要重复维护一份共同账本 |
| 会定期整理账务的用户  | 手机零散记录，电脑导入官方账单      | 后续导入能补全、核对已有记录，不重复计账  |

首版不面向复杂家庭财务、多人合伙、企业报销或投资组合管理。这些场景会引入另一套权限和核算需求。

还有一个应明确的产品边界：**透明不等于监督。** 产品可以提供双方同意的查看能力，但不默认做消费审判、异常消费提醒给伴侣、强制解释支出等功能。

### 3. 核心价值：减少录入，保持真实，解释归属

**第一，记录成本足够低。**

截图记账的目标不是“展示识别出来的文字”，而是让用户获得一笔可用账单。理想体验是：

> 选择截图 → 自动处理 → 已完成，或者只补充一个确实无法确定的信息。

“自动”可以逐步提升：先辅助核对，再对已验证的常见场景自动入账。不必把每笔账都变成审核任务，也不能把未知付款账户猜成确定事实。

**第二，手机记录和电脑对账能够相互补充。**

截图常常先到，官方账单后来才导入。后来的账单应该帮助确认或补充已有交易，不能天然产生第二笔消费。

这会成为星账比“截图转表单”更重要的产品能力：**同一笔交易可以有多个证据，但只产生一套有效账务。**

**第三，把“谁的账户”和“谁的钱”分开。**

例如：

- 你的银行卡实际余额为 10,000 元；
- 其中 3,000 元属于对象，由你保管；
- 对象的银行卡里有 2,000 元属于你。

那么：

| 展示指标               | 结果       |
| ------------------ | -------- |
| 你这张银行卡的实际余额        | 10,000 元 |
| 你在这张卡里拥有的钱         | 7,000 元  |
| 对象替你保管的钱           | 2,000 元  |
| 你拥有的资产，假设没有其他资产及负债 | 9,000 元  |

银行卡余额不能被改成 7,000 元，也不需要另建一张虚构的“情侣卡”。

绑定后的首页建议优先展示\*\*“我拥有的钱”\*\*，同时说明其中多少由对象保管；账户页面展示真实账户余额及归属构成。双方合计资产按真实资金只计算一次，不能把代管金额重复加上。

这里还必须区分：

- **代管**：钱仍属于原主人，只是放在另一人的账户里。
- **赠与**：资金归属发生变化。
- **借款**：形成债权债务，不能当作代管。

初期先支持代管，不必顺带开发完整借贷系统。

### 4. V1 / V1.5 / V2 路线

**建议让版本分别解决三个问题：个人能持续用、两个人能看清、截图能更自动。**

| 版本              | 产品目标               | 必须交付                                        | 发布判断                                  |
| --------------- | ------------------ | ------------------------------------------- | ------------------------------------- |
| **V1：个人可持续使用**  | 手机与电脑能维护同一本可靠的个人账本 | 个人账户、日常记账与修改、文件导入、批量截图辅助记账、统计、登录同步与恢复       | 能完成一段真实日常使用；截图与文件重复出现时不重复计账；换设备可恢复    |
| **V1.5：情侣关系透明** | 各自独立记账，绑定后看懂双方资金   | 双向绑定、绑定后首页、对象近期交易与账户只读查看、真实账户内的代管归属、解除绑定    | 账户实际余额与个人拥有资产分别正确；双方合计不重复；解除关系后个人账本完整 |
| **V2：更自动的记录体验** | 减少从截图到可用账单的操作      | 已验证场景自动入账、低确定性项集中补充、截图与官方账单自动核对、更便利的移动端输入入口 | 自动化覆盖提高，同时重复、误记和纠正成本保持可控              |

#### V1：单人优先，但截图是核心功能

截图不应被降为发布后再考虑的附属功能，因为它决定你在手机上是否愿意持续使用。

V1 可以允许用户核对识别结果，但要做到多图处理、结果保留、失败可重试、保存后真正进入账单和同步。文件导入也必须与截图采用一致的账务解释。

**AI 可作为实现截图识别的手段进入 V1。** 不必等到 V2 才使用 AI；V2 提升的是自动化程度，而不是首次接入模型。

#### V1.5：把情侣价值真正做出来

绑定后建议提供：

- 首页的“我的资产”，包含对象代管的部分；
- “由我保管”和“由对象保管”的解释；
- 对象近期交易与账户入口；
- 每个真实账户中的资金归属编辑。

首版关系权限可以简单：双方明确同意后，相互查看约定范围内的账务。**查看权和修改权仍需分开**，默认各自修改自己的账务。

涉及另一方的资金归属变更，应有明确确认规则和变更记录。可以先采用“账户持有人提出、资金归属方确认”，无需为此开发聊天系统。

#### V2：优先缩短截图操作，再决定安装版

分别看待三个目标：

1. 在星账内选择截图并自动处理；
2. 从其他应用的分享入口交给星账；
3. 不打开星账也能触发处理。

它们的实现条件不同，不能合并成一句“支持自动截图”。

先把第一项做顺，再按 Android、iOS 的实际能力验证后两项。是否开发安装版，应由**能减少多少操作、是否可靠**决定，不作为产品成熟的形式要求。

### 5. 现在不要做什么

| 暂不做                   | 原因                         |
| --------------------- | -------------------------- |
| 独立于真实银行卡和支付账户的“情侣资金池” | 会破坏余额与现实账户的对应关系            |
| 双方共同编辑全部交易            | 会引入修改责任与冲突问题，当前相互查看已经有明显价值 |
| AA 分摊、催款、复杂借贷结算       | 与代管归属是不同业务，容易把产品变成关系结算工具   |
| 情侣聊天、纪念日、互动任务         | 不能直接改善记录和资金理解              |
| 复杂的逐笔分享权限矩阵           | 首批用户可以采用清楚、简单的共享范围         |
| 全平台原生客户端同时开发          | 会分散截图、账务与同步闭环的开发资源         |
| 无条件自动入账、AI 自主调整余额     | 识别错误会直接变成账务错误              |
| 先做通用多人家庭账本架构          | 当前没有足够真实场景支撑这笔复杂度投入        |

特别是，**代管金额发生变化后，不应默认每一笔消费都要询问“花的是谁的钱”**。建议初期默认账户持有人支出使用其本人份额；只有明确涉及代管资金时再选择归属。本人份额不足等情况下再要求处理，而非静默挪用另一方资金。

这条规则需要在 V1.5 开发前用真实使用案例确认。

### 6. 数据模型未来需要预留什么

“预留”意味着避免当前实现堵住未来扩展，不意味着现在就把全部关系功能建完。

| 概念           | 需要表达的内容                               | 建议落地时机          |
| ------------ | ------------------------------------- | --------------- |
| 用户、账本与真实账户归属 | 谁拥有个人账本、谁持有账户；不能拿“当前登录者”替代所有归属判断      | V1 明确           |
| 多来源与单笔交易的关联  | 截图、文件记录可以指向同一交易；保留各自原始证据              | V1 重点完成         |
| 识别任务与正式交易分离  | 识别中、待补充、失败不等于正式入账；重试不能重复创建交易          | V1 完成           |
| 字段来源与用户修正    | 金额、时间、账户等来自原始证据、规则、模型还是用户；重识别不能覆盖用户修正 | V1 按必要字段保留      |
| 关系与授权        | 谁与谁绑定、授权范围、生效和解除状态                    | V1.5 实现，V1 避免写死 |
| 账户中的资金归属     | 一个真实账户可包含不同人的份额；归属变化可追溯               | V1.5 实现         |
| 消费归属         | 出钱的人、账户持有人、实际消费的人可能不同                 | 预留概念，按真实场景逐步实现  |

继续保护现有三个事实：

- `Transaction` 表示经济事件；
- `BalanceMovement` 表示真实账户余额变化；
- `ConsumptionEffect` 表示消费统计影响。

**资金归属变化应独立表达。** 同一张卡内，将 500 元从“属于我”调整为“属于对象”，不会使银行卡实际余额减少 500 元；也不能天然算作 500 元消费。

未来可以用独立的归属变更记录承载这一事实，具体结构留到 V1.5 设计，避免现在污染已有账务模型。

另一个必须提前确定的边界是：**关系绑定不改变原始账务所有权，解除绑定首先撤销查看权限。** 尚未处理的代管资金要保留清楚的历史和待处理状态，不能因解绑自动消失或被系统虚构为已归还。

### 7. AI 开发时如何拆任务

不要给 AI 一个“完成截图记账”或“完成情侣模式”的大任务。应按**一个用户结果贯穿界面、业务、存储和验证**拆分。

建议顺序如下：

| 任务            | 单次交付结果                   |
| ------------- | ------------------------ |
| 1. 个人账务基础闭环   | 新增、修改、删除、恢复后，账单、余额和消费一致  |
| 2. 文件导入闭环     | 正常记录完成入账，其余记录有清楚去向并可继续处理 |
| 3. 单张截图完整入账   | 识别、补充、保存、重开形成完整路径        |
| 4. 截图与文件去重补全  | 同一交易两种来源进入后，只计算一次，证据保留   |
| 5. 批量截图与任务恢复  | 多图独立处理，中断后继续，失败可单独重试     |
| 6. 账户同步与恢复    | 手机和电脑看到一致账务，换设备能找回       |
| 7. 关系绑定与只读查看  | 双方同意绑定后可以查看，解除后权限失效      |
| 8. 真实账户中的代管归属 | 账户余额保持真实，个人资产和双方合计正确     |
| 9. 绑定后首页      | 展示已验证的个人资产、代管构成及对象入口     |
| 10. 自动化提升     | 按具体截图场景逐项降低确认次数          |

每个任务只需要一张简短任务卡，固定写清：

- **用户结果**：用户完成什么操作后能看到什么；
- **修改边界**：实际入口、相关业务路径、需要保存的数据；
- **保护规则**：哪些账务关系必须保持；
- **验收案例**：一个正常场景及相关失败、重复或中断场景；
- **完成证据**：区分本地测试、浏览器、真实截图、真实云端和用户验收。

AI 识别任务还要分别衡量**字段正确率、自动完成比例和用户纠正成本**。不能用“OCR 返回成功”替代“生成了一笔正确账单”。

**下一步应先冻结 V1 的个人闭环和截图体验，同时把“真实账户不变、资金归属独立、关系仅增加授权与视图”作为长期架构边界。** 这样既能尽快做出你们能用的版本，也能让后续情侣能力自然接上，而不必重新设计一套账本。

**一、当前截图流程及具体问题**

当前实际链路是：

选择单张图片 → 浏览器 Tesseract 识字 → `parseScreenshot()` 解析 → 保存草稿 → 用户核对 → `saveCapturedRecord()` 记账。

| 环节    | 已确认实现                             | 对使用体验的影响                  |
| ----- | --------------------------------- | ------------------------- |
| 图片选择  | 单张 PNG/JPEG/WebP，上限 12 MB         | 多笔付款需要反复选择                |
| OCR   | 本地 Tesseract，中英文模型；返回纯文本          | 后续解析拿不到文字位置，难以判断哪个值属于哪个标签 |
| 金额    | 优先取文本中第一个带货币符号的金额                 | 遇到原价、优惠、实付、退款并存时可能选错      |
| 字段    | 按标签同行或下一行取值                       | OCR 换行、左右列错位会传导为字段错配      |
| 时间、平台 | 正则匹配时间；通过“微信/支付宝”文字判断平台           | 版式变化、截图缺失平台字样时可能识别不全      |
| 类型、状态 | 按全文关键词判断                          | “支付成功＋退款处理中”等页面存在误判风险     |
| 退款身份  | 即使判断为退款，截图 key 的来源类别仍写为 `payment` | 需要修正支付与退款的身份区分，避免关联或去重错误  |
| 组合付款  | 保存入口直接抛出 `COMPOUND_CAPTURE`       | 即使识别完全正确，仍然无法走完保存         |
| 保存    | 有过期检查、重复检查及业务记账调用                 | 已有基础可以复用，不需要另建账务系统        |

代码依据：[OCR](https://github.com/AsteriaAnna/star-ledger2/blob/63ab2e2/app/apps/web/src/ocr.ts)、[截图解析](https://github.com/AsteriaAnna/star-ledger2/blob/63ab2e2/app/apps/web/src/importer.ts)、[截图保存](https://github.com/AsteriaAnna/star-ledger2/blob/63ab2e2/app/apps/web/src/captured-record.ts)、[页面入口](https://github.com/AsteriaAnna/star-ledger2/blob/63ab2e2/app/apps/web/src/main.ts)。

这里要区分：**上述规则和限制是代码事实；它们在真实截图中分别造成多少失败，需要用样例定位，不能凭推测分配责任。**

**二、产品目标：自动填好，尽量少确认**

建议第一版用户流程：

1. 手机截图后，打开星账，一次选择一张或多张。
2. 每张图片独立处理，先完成的先显示。
3. 普通付款直接生成填好的账单卡片，可一键保存；多张可批量保存。
4. 只有金额、付款账户、交易性质等关键字段不确定时，突出需要补充的字段。
5. 保存后立即进入账单、余额和统计，并进入现有同步流程。

商户名、分类可以自动建议，缺失时允许使用“未命名商户／其他”，不阻塞金额等信息明确的账单。**不能因为分类不确定，让用户重新核对整张表单。**

首版保留一次保存动作。后续只对通过真实评测的明确场景开放自动入账，并提供撤销。

“截图后自动获取图片”需要单独处理。网页选图识别可以先完成；系统分享入口可作为后续增强。PWA 接收分享依赖安装和浏览器支持，不能承诺 Android、iOS 具有相同能力。[MDN](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Manifest/Reference/share_target?utm_source=chatgpt.com)

**三、OCR、视觉模型、规则分别负责什么**

| 层次   | 职责                                       | 为什么需要                |
| ---- | ---------------------------------------- | -------------------- |
| OCR  | 提取文字、坐标、识别置信度                            | 保留可核对的数字与原文证据        |
| 视觉模型 | 理解页面结构，区分实付、优惠、退款；提取商户等候选字段              | 应对模板变化和纯文本错位         |
| 规则解析 | 标准化金额、时间、状态、资金渠道，检查字段关系                  | 让截图与官方文件产生一致的业务含义    |
| 业务记账 | 生成 Transaction、Movement、Effect，处理退款与资金分摊 | 保护已有账务规则             |
| 用户核对 | 解决图片本身无法说明的事实                            | 例如截图没有账户信息，模型也不能凭空知道 |

腾讯云通用 OCR 可以返回文本框坐标，因此接入时应保留结构化结果，不能再次压成纯文本后沿用全部旧规则。[cloud.tencent.com](https://cloud.tencent.com/document/product/866/33526?utm_source=chatgpt.com)

建议统一输出一份**识别候选记录**，包含：

- 平台、页面类型、交易状态、金额、时间及时间精度；
- 商户、商品、付款渠道、银行卡尾号、组合付款明细；
- 支付单号、退款单号、原支付单号，分别保存；
- 每个字段对应的原文或图像区域；
- 未知字段、冲突字段、识别服务及解析版本。

**识别结果、用户修正、最终账务应分开保存。** 原始证据不能被用户修改账单时覆盖；也不要求现在把全项目所有输入统一改造成 SourceRecord。

关键规则建议如下：

| 场景                 | 处理方式                             |
| ------------------ | -------------------------------- |
| 原价、优惠、实付同时出现       | 提取各自含义，以实际支付金额生成消费；不取“第一个数字”     |
| 支付页面显示“已退款”        | 区分原支付状态与独立退款事件，不能直接把整张图当作一笔退款    |
| 亲情卡                | 明确受益人／付款人视角；本人受益的代付消费不扣本人账户      |
| 花呗付款               | 识别为负债资金来源，不当作普通余额账户              |
| 组合付款               | 提取分项，验证合计等于实际付款，再进入分摊记账          |
| 付款渠道缺失             | 只询问账户，不要求重新填商户、金额、时间             |
| 同一交易截图与 Excel 重复导入 | 按平台、账本归属、事件类别及可靠单号关联；保留两份来源，只记一笔 |
| 无单号、同金额同商户         | 仅提示相似，不能直接判重；可能确实发生两次消费          |

模型不能直接生成可执行账务操作，也不能靠自己报告“置信度 99%”决定自动入账。必须结合字段证据、规则检查和真实评测结果。

**四、推荐部署与识别路线**

使用已有 CloudBase 承接识别任务，不新增一套常驻服务器：

[原文 Mermaid 渲染样式已移除；流程：批量选图 → 上传与任务保存 → 主识别 → 字段标准化与规则检查 → 可保存候选或必要补充 → 现有业务记账。]

建议分两步选型：

- \*\*先做对照：\*\*同一批真实截图比较“腾讯 OCR＋规则”和“视觉模型结构化提取＋规则”，沿用本地 OCR 作为现状基准。
- \*\*再定生产主路：\*\*谁的整单正确率、速度和成本更合适，谁作为默认。辅助服务只用于明确的缺失或冲突，不让每张图必经两次调用。

因此，腾讯 OCR 是优先接入候选，**不是提前确定的最终赢家**。视觉模型若实测更好且成本更低，可以成为主识别，但账务判断仍由规则和现有业务层负责。

后台处理还需明确：

- 上传成功并取得任务编号后，关闭页面不影响服务端继续识别；重新打开能取回结果。
- 上传未完成就关闭页面，不能承诺服务端已接收。
- 服务端先保存识别结果，客户端通过现有账务入口提交；首版不在服务端再造一套记账逻辑。
- 每张图有独立任务和重试标识；重复回调、重复点击不重复记账。
- 密钥放服务端；图片按用户隔离，成功提取后删除，失败图片设置短期清理期限。
- 开启云识别后，要更新目前“图片留在你的设备”的文案。

**五、成本估算**

以下是查询到的公开价格与假设测算，不是实测账单。

腾讯云低调用量后付费：普通 OCR **0.15 元/次**，高精度 **0.50 元/次**；部分服务有每月免费额度，实际需要检查账户对应资源包。[cloud.tencent.comcloud.tencent.com](https://cloud.tencent.com/document/product/866/17619?utm_source=chatgpt.com)

以北京地域 `qwen-vl-plus` 公开价格作视觉模型示例：输入 **0.8 元/百万 tokens**，输出 **2 元/百万 tokens**。该报价不代表已选择此模型，也不能套用到其他型号。[help.aliyun.com](https://help.aliyun.com/en/model-studio/model-pricing?utm_source=chatgpt.com)

假设每张截图计费输入 2,000 tokens、输出 500 tokens：

`单张模型成本 = 2000×0.8/100万 + 500×2/100万 = 0.0026 元`

| 方案                   | 单张估算     | 两人共 600 张/月 | 10 人共 3,000 张/月 |
| -------------------- | -------- | ----------- | --------------- |
| 普通 OCR，全量调用          | 0.15 元   | 90 元        | 450 元           |
| 高精度 OCR，全量调用         | 0.50 元   | 300 元       | 1,500 元         |
| 示例视觉模型，全量调用          | 0.0026 元 | 1.56 元      | 7.80 元          |
| 示例视觉模型＋20% 普通 OCR 复核 | 0.0326 元 | 19.56 元     | 97.80 元         |

表中统一**未扣免费额度，未含重试、云函数、存储、流量和现有套餐费**。图片分辨率和输出长度会改变模型 token 消耗，必须记录 API 实际 usage。

这个估算说明：**不能默认传统 OCR 比视觉模型便宜。** 小规模使用更应该先比较整单效果，再看真实单张成本，不建议一开始购买大额资源包。

**七、发布验收标准**

以下是**建议目标，不是当前达成情况**：

| 维度    | 验收标准                                            |
| ----- | ----------------------------------------------- |
| 基础场景  | 微信、支付宝普通付款，以及退款、亲情卡、花呗、组合付款均有真实样例               |
| 评测方式  | 15 张旧样例用于定位；另外保留未参与调规则的截图作为验收集，建议至少 100 张，分场景报告 |

| 缺失与异常 | 截图未展示的关键字段不编造；识别失败可补充保存，不出现无法继续的死路              |
| 资金正确性 | 验收集里，失败／待支付不产生实际扣款；亲情卡、负债、退款及分摊按预期影响账务          |
| 去重    | 原图重复、裁剪后重复、截图与文件交叉导入均有测试；无单号相似记录不误删             |
| 批量与恢复 | 一次选择 10 张，逐张显示结果；单张失败可重试；已保存任务和修改内容可恢复          |
| 速度    | 目标网络与设备下，单张上传完成至结果的 P50 ≤5 秒、P95 ≤15 秒；实际测量后判定  |
| 完整闭环  | 保存 → 刷新 → 修改 → 同步到电脑，账单、余额、统计结果一致               |
| 成本    | 能看到实际单张成本、重试率与辅助识别触发率；达到限额时明确提示并保留任务            |
