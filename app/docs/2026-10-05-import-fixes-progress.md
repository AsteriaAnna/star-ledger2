## 用户结果与机制

- 微信提现明确的 0.00 元手续费不再被拒绝；主资金端为零钱，文件银行卡字段作为目标端。充值的零钱目标和明确花呗还款目标交给相同账户解析服务。原始行字段保留，不因资金语义规范化丢失。
- 账户确认保持当前批次一次性选择选项；选择记忆时，对所有本地批次尚未关联的资金端重新匹配。只补未知端，不覆盖已确认端。花呗目标也记忆并重评估同类还款，不逐条创建负债账户。
- 已确认的银行名称、卡类型、尾号身份跨微信/支付宝复用，显示名称可以是工资卡。相同尾号但没有已确认身份仍只是候选；不同归属、冲突或明确忘记不复用。钱包记忆继续限定来源，不把所有“余额”混为一个账户。
- 账户详情展示来源别名，并提供登记和停止记忆。登记来源名称不改变账户显示名称，不自动更改历史已绑定流水；尚未绑定的导入可以重新匹配。
- 退款编号前缀解释在文件适配、应用解析及晚到原消费处理间共用，覆盖实际支付宝后缀。明确原订单不存在时，不建议另一笔同名消费。导入里的退款建议来自来源证据，并通过账务约束筛选；详情的“查找其他账单”才展开完整合法集合。
- 导入页面仅列新增账单、重复记录、待处理；不再展示“无财务影响”“可稍后补充”队列。来源的失败支付仍完整接收，不记不存在的扣款，也不当成软件导入失败计数。
- 移走账户页常驻数字规则；设置增加关于与帮助，手机导航改为设置；原始证据入口明确为来源原始字段。GitHub同步入口尚未撤下，等CloudBase恢复/迁移实测后处理。

## 实际验证

在本地构建、新建空浏览器账本中导入用户提供的两个169行Excel文件。脚本只接受本地文件路径；私人文件、交易名称、订单和逐行内容不进入仓库。

| 场景 | 结果 |
| --- | --- |
| 微信 → 支付宝，两份都先导入，逐项确认账户 | 账户决策4次：3次主资金账户、1次花呗目标；后续相关批次自动补齐 |
| 支付宝 → 微信，同样逐项确认 | 同为4次；相同326笔实际交易、28条退款关系 |
| 三笔微信提现 | 零钱转银行卡；手续费分别1.50、0.00、4.50元；本金和手续费分别核算 |
| 支付宝退款 | 文件内有原单的19笔自动关联，原版本仅1笔；2笔缺原消费不误关联 |
| 最终待处理 | 3条微信退回关系，未自动猜测；账户/转账目标问题为0 |
| 账户改为工资卡、跨来源复用、别名入口 | 确认身份后识别；账户详情可看到已记住的来源并保存新别名 |
| 刷新 | 操作数不增加；问题和绑定保存；浏览器无脚本错误 |

4次是用户账户决策数，不是全部鼠标点击数。导入两份文件、打开确认窗口、选择/填写和保存仍有操作。此轮未测真实手机、OCR图片、真实云端或国内无VPN网络。

底层测试380项通过；核心和Web类型检查、Web构建通过。新增测试针对这次确实复现的手续费、跨批次账户、跨来源改名、花呗目标、别名和退款编号缺陷；没有新增通用测试矩阵。
