# M5.1 账户确认与导入回归（2026-10-02）

基线 `2fac970c`，实现提交 `1dc14a4`，分支 `m5-core-flows`。不合并 main，不宣布 M5.1 完成。

## 本次实现

- 应用层 `planImportAccountAnswer`：新建/绑定账户，同批同渠道一次补齐。账户、资金绑定、带角色的记忆、Attention 和 Session 在同一次本地事务中落盘。
- Web adapter 在 `mutate` 内读取最新状态。过期问题、已被修改的绑定、同步冲突不留下半完成结果；不改原始证据及消费统计。
- 页面显示账户确认入口、渠道与交易对方；旧批次的未完成问题仍可访问，无问题历史批次折叠。
- V2 记忆可在设置中查看/停止；新增 payload 带可读 identity，兼容旧 payload。
- `REVIVE_EXISTING` 经过金额/日期/账户/组合支付解析，不能强制 Ready。
- 购买事件向 LedgerIntent 传递已识别分类。
- 支付宝明确退款单号后缀用于原单匹配；同批原消费先建立临时账本投影，再解析退款，避免文件行顺序影响强关系。
- 重置账本和清除演示同时清除 ImportWorkspace。

## 验证

基线 CI 的 core 成功，浏览器失败于等待旧 `importRevision`。浏览器脚本改为观察持久化 Session + Outcome，保留种子旧队列修正测试。

本地已通过 core/web 类型检查、平台边界、全部 36 个测试文件、生产构建，以及完整桌面/手机 Chromium 导入回归的 8 组场景。最后复跑曾遇到环境 Chromium 缓存丢失；恢复临时浏览器并让测试使用独立临时端口后，最新代码的 8 组浏览器回归再次全部通过。测试启动失败也会关闭 HTTP server。远端 CI 尚未运行，因为推送被自动审批拦截，需要用户明确授权发布到现有 M5 分支。

新增测试覆盖账户分组补齐、后续导入记忆、过期回答和已绑定账户拒绝、证据/消费不变；回收站重导完整解析；退款行在原消费前的同批关联。分类测试明确断言识别分类被保留。

## 收口门槛

[Issue #12](https://github.com/AsteriaAnna/star-ledger2/issues/12) 记录以下未完成项：

1. 组合支付、来源变化、金额/日期/状态/性质、消费分摊和另一端账户的 typed answer 与恢复执行。
2. PENDING 交易账户回答需修改 posting plan，不能伪造 Movement。
3. 后续批次才到达原消费时，重新检查既有未关联退款；旧浏览器曾覆盖此能力，迁移脚本不代表免除验收。
4. 删除前有用户修改时，重导同一证据不得静默丢失修改。
5. SOURCE_UPDATE 证据已附着不代表账务决策完成，重试不能仅凭 exact evidence 消除未回答问题（关联 #6）。

旧 review queue 保留兼容入口。已有的同批关联、退款晚于已有原单测试，不代表全部退款生命周期完成。
