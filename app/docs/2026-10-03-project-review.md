审查日期：2026-10-03。维护范围：`app/`；`legacy-duo/` 只读。

## 1. 当前结论

项目有可继续演进的账务核心，当前不需要整体重写。但导入的证据、用户决定和恢复生命周期存在明确缺口，不能宣称底层风险结束，也不能把 M5.1 标记为完成。优先完成导入闭环，再推进其他页面。

本次已将上一轮实现推送至 `m5-core-flows`，代码 HEAD 为 `66fd47bc09bb85f4f3a57aa0082f6e1fd56a800e`。对应 [Draft PR #9](https://github.com/AsteriaAnna/star-ledger2/pull/9)，尚未合并 main，也不等于已部署给用户。main 的 M4 合并基线是 `dc20c39f385050c26a81bf254ba041d79e5a73a9`。

[代码 CI 37016401726](https://github.com/AsteriaAnna/star-ledger2/actions/runs/37016401726) 的 core、import-browser 两个 job 已通过。上一轮验证包括 36 个底层测试文件、8 个浏览器导入场景；这里的 36 是文件数，不是用例总数。本次另外运行了合成数据生命周期诊断及 `npm run typecheck`。诊断发现三项违反预期的行为；CI 通过并不覆盖这些缺口。

本轮交付为审查报告和可重复运行的诊断，不包含这三项业务缺陷的修复。审查不是全量安全审计、性能测试或商业软件实机评测。

| YNAB 信用卡匹配说明 [Y1] | 自动关联综合金额、日期和来源含义；匹配已有手工记录后减少重复批准，并提供可查看的匹配结果 | 强证据自动处理，歧义才问；保留可解释、可撤销的关系结果。相同金额不足以自动合并 |
| Monarch 官方入门说明 [M1] | 账户、交易整理、规则与报告形成用户流程；编辑可以形成以后使用的规则 | 问题回答应沉淀为可查看/可遗忘的记忆，页面围绕任务组织；规则与本笔事实分开 |

### 保留的方向与不能照搬之处

- 保留金额整数分、消费效果与账户资金变化分离、应用服务统一产生账务命令、原始证据与修改历史分开、冲突不静默合并的原则。此次审查未发现必须替换整套核心的证据，但也未穷尽所有账务不变量。
- Actual 的“先选账户再导入”适合单账户文件。微信/支付宝文件可能涉及多个资金渠道，星账应继续先导入，再按未知渠道集中询问。
- 类别拆分与组合支付是两个维度：多个分类不等于多个付款账户。不能直接照搬分类 split 模型完成组合支付。
- 未知付款账户不等于外部代付；还款不等于消费；对账差额不应自动伪装成收入或支出。
- Firefly 的服务器队列不是本地优先应用必须增加的架构。星账需要可恢复的本地状态和清楚的提交边界，不需要为了对标引入服务器。
- 商业产品也有匹配取舍、平台差异和持续修正。对标用于提炼验收标准，不是证明某个实现天然正确。

## 4. 已复现的合并阻塞问题

运行：在 `app/` 下执行 `node scripts/audit-m5-lifecycle.ts`。快照结果见同目录 `2026-10-03-lifecycle-findings.json`。全部为合成数据；调用真实应用服务和账务解释器，不是浏览器或持久化故障注入。脚本退出 0 仅表示诊断执行完成，必须检查 `violation`；不能将它当成通过的回归测试。

### P1-A：删除重导覆盖已有手工更正

- 步骤：导入 1000 分 → 用户改为 1200 分并修改备注 → 删除 → 重导完全相同的来源。
- 结果：`REVIVE_EXISTING` 后金额变回 1000 分，备注从 `user-note` 变回 `source-note`。
- 路径：`application/import-commit.ts` 重建 replacement；`import-execution.ts` 先 RESTORE 再用来源 replacement 调用 Correction Service。
- 原因：恢复交易与根据来源重新解释交易被绑定成一个动作；当场生成 expectedSnapshot 只能防并发，不能保护更早的用户编辑。
- 修复方向：相同证据的恢复保留用户修改；来源确有变化时独立进入证据差异决定。删除重导开关及默认值需形成明确产品契约，不悄悄改变既有策略。
- 验收：金额、分类、备注、账户、关系均覆盖“修改—删除—重导”；变化来源不能静默重置；重复恢复幂等。

### P1-B：证据已附加，但未回答的问题在重试时消失

- 步骤：导入 1000 分 → 同一来源新证据显示 2000 分 → 保存 SOURCE_UPDATE 证据并保留待核对 → 对同一会话重新 prepare。
- 结果：`SOURCE_UPDATE` 变成 `SKIP_DUPLICATE`，Attention 从 1 变 0，但账本仍是 1000 分。
- 路径：`importing/dedup.ts` 命中已存在的 exact raw evidence；`ImportStatementService.prepare` 未参考未解决的决定，`saveSessionSnapshot` 整体替换问题。
- 边界：复现的是应用服务的同会话重试路径；不能宣称当前重新上传新文件一定会删掉旧会话问题。当前 UI 本身尚缺完整恢复入口。
- 修复方向：分开表达“证据已接收”“账务已提交”“差异已回答”；持久化回答及其针对的证据版本。恢复不能把 BLOCKED 降为普通 duplicate，计数也不能把原 COMMITTED 改成重复跳过。
- 验收：保存证据、保存决定、提交账务前后中断并重试；问题与决定保持一致，统计不漂移，用户修改不丢失。

### P1-C：同订单先失败后成功导致整批计划失败

- 步骤：同一批同一来源身份先 FAILED，再 SUCCESS 且 raw 不同，同时放入一条无关正常交易。
- 结果：依次分类为 NO_EFFECT、SOURCE_UPDATE、INTERPRETED；计划阶段抛 `TRANSACTION_UNAVAILABLE`，没有任何交易提交。
- 路径：`prepare` 在确认首条可入账前就写入 batchSources；第二条被当成已存在交易的新证据；`planImportCommit` 生成一个实际不存在的目标 ID。
- 修复方向：本批证据分组必须区分“已观察身份”和“有可用账务实体”，先判定整个证据组的状态演进；冲突组不能构造不存在的证据附加目标。
- 验收：失败/处理中/成功/缺金额/退款等排列组合；交换行顺序；同组不确定时保持问题，但无关合法记录仍可安全处理。保留计划及提交的原子性，不用部分写入掩盖错误。

## 5. 静态确认的缺口与尚待专项验证的风险

| 优先级 | 状态与缺口 | 下一步 |
|---|---|---|
| P1 | ACCOUNT 之外及 blocking 的问题多为 UI 占位；split、来源变化、金额/日期/状态/含义、消费分配、转账两端未完整回答 | 实现 typed answer → service → 最新状态校验 → 原子保存 → 更新结果；不在 main.ts 拼写底层实体 |
| P1 | 账户回答服务只接受 SUCCESS；PENDING 记录的账户问题无法按现有路径完成 | 改 posting plan，不能为未成功交易提前制造资金变化；覆盖状态晋升 |
| P1 | 已单独入账的退款不会因以后批次导入原消费而自然重新解析 | 增加跨批关系重评估，强关联自动处理，弱候选提问；覆盖撤销、修改、多退款和超额 |
| P1 | 显示旧会话不等于 PROCESSING 能执行恢复；工作区未持久化完整解释/回答状态 | 定义重算版本或持久化解释，加入可执行恢复入口和各阶段故障注入 |
| P2 | 手工/OCR/官方文件尚缺完整跨来源同事件匹配契约 | #6 内明确 SourceIdentity、不可变证据、交易之间基数；弱证据仅候选，不按相同金额强并 |
| P2 | 来源 raw 变化未区分财务变化与无关文本变化 | 形成字段差异及优先级规则：哪些自动附加，哪些需要决定，哪些保留用户值 |
| P2 | 已解析计划提交时虽读取最新账本，但不重新做完整去重/解析 | 验证多标签、同步插入、账户删除等并发下的过期计划；拒绝或重算，不能重复入账 |
| P2 | Web 使用 IndexedDB 状态保存及内存账务适配，不是 SQLite 运行时 | 文档修正运行时区别；SQLite 测试不能替代 Web 崩溃、配额、并发和恢复测试 |
| P2 | 旧 Draft/OCR/修改流程仍与 V2 共存 | 跟踪迁移矩阵；完成等价能力后再删旧入口，不能用删测试掩盖丢失能力 |
| P2 | 全量操作重放、备份工作区合并和跨设备生命周期尚未专项压测/故障验证 | M6 量化规模、迁移、冲突与恢复；目前不能承诺大账本性能或恢复完整性 |

这些条目中前三个诊断有运行证据；本节不得被误读成每项都已做端到端复现。未做完整依赖/安全审计；既有 [#8](https://github.com/AsteriaAnna/star-ledger2/issues/8) 继续作为发布门槛，不能据此宣称零漏洞。

## 6. 下一步完整执行顺序

### 第一优先级：M5.1-A，先补契约并修三项缺陷

产出：小范围 M4 补充决策，明确恢复与来源变更、证据接收与决定完成、本批状态演进；将三个诊断改写为断言正确行为的回归用例，然后分别修复。业务修复按小提交交付，避免再造通用 workflow 引擎。

退出条件：三项正确行为测试通过；相同输入重试结果稳定；不会丢手工修改、隐藏问题或生成不存在的目标。此项完成前保持 PR #9 Draft。

### 第二优先级：M5.1-B—F，完成一个可恢复的导入闭环

| 顺序 | 工作内容 | 必须通过的验收 |
|---|---|---|
| B | typed Attention 回答：来源变化、字段缺失、含义、组合支付、消费分配、转账两端、退款关系 | 每个展示的问题有实际解决路径；过期回答不生效；取消不误记决定 |
| C | SUCCESS/PENDING 账户、同渠道集中处理与记忆、账户不可用处理 | 首次未知才问；处理中不动余额；记忆可查看/遗忘；不同身份不串用 |
| D | 同批与跨批来源/退款关系，手工与官方来源匹配边界 | 晚到原消费、退款先到、多个候选、删除恢复、用户改动、重复来源都不重复记账 |
| E | 会话恢复、逐记录结果、异常重试、多标签并发 | 刷新/关闭/失败后可继续；COMMITTED/NO_EFFECT/BLOCKED 统计保真；中断点覆盖解析、证据、账务、结果保存 |
| F | 浏览器/真实数据回归，清理 V1 入口及测试迁移 | 原有能力逐项保持；微信 169 条、支付宝 169 条既有样本按固定预期复核；重复导入、还款目标、晚到原消费必测 |

338 条真实样本是后续门槛，本次诊断没有重新跑它们，也不提交私人账单。问题继续集中在 [#12](https://github.com/AsteriaAnna/star-ledger2/issues/12)；[#11](https://github.com/AsteriaAnna/star-ledger2/issues/11) 的逐记录结果已有代码，不因存在代码就忽略恢复验收。[#6](https://github.com/AsteriaAnna/star-ledger2/issues/6) 完成基数契约后再关闭。

M5.1 合并条件：上述门槛完成、核心与浏览器 CI 通过、报告中的 P1 关闭并有测试证据。之后才替换旧流程和移除兼容入口。

### 第三优先级：M5.2—M5.6 完整页面接入

1. M5.2：详情页统一接 Correction Service；金额、账户、时间、类型、分类、名称、备注统一提交；退款 detach/revalidate/relink；有真实关系冲突才提问。验收修改前后余额、消费、关系与历史一致。
2. M5.3：退款关系展示、候选选择、解除/重连；退款事实可独立存在。验收多次退款、超额、原消费删除/恢复/修改及跨批到达顺序。
3. M5.4：账户明细和 running balance；实际余额先记录 Observation，明确选择校准才建立 Anchor。验收负债符号、未建账余额、日期边界与冲突阻断。
4. M5.5：首页、分类、日期图表统一消费贡献查询，聚合携带交易 IDs。验收图表合计等于下钻明细，退款、代付与转账口径一致。
5. M5.6：“花钱/收钱/转钱”调用 Record Service，不走导入会话；支持未知账户、明确代付和组合支付。验收与等价导入记录产生一致的账务效果。

上述各项有服务基础，不代表页面已经完成；每项完成均应以用户任务端到端验证关闭。

### 第四优先级：M6 数据可靠性与适配

- Web/PWA：正式明确存储事务、配额、损坏检测、迁移与回滚；备份恢复后重新计算并验证账务不变量、关系、来源证据、记忆和工作区引用。
- GitHub 同步：真实双设备离线写入、上传失败、重复下载、冲突解决、删除/恢复与重新绑定端到端验证；不能只依赖 FakeSyncProvider。
- 明确工作区是否跨设备接力。未决定前保留本地工作区边界，账务同步不携带所有瞬时处理状态。
- 跨平台适配先建立能力矩阵，Windows/Android/iOS 逐个平台验收持久化、导入和恢复，不一次性承诺所有平台发布。
- 建立 1千/1万/5万笔合成账本基准，分别测冷启动、导入、重放、查询和备份的耗时、内存及体积；这些规模是拟定测试档位，不是当前性能承诺。根据实测决定索引、增量投影或快照，不提前重写存储。

### 第五优先级：M7 发布质量

- 依赖安全与供应链：处理 #8，记录适用性与修复验证；不直接 `npm audit fix --force`。
- 空状态、失败提示、危险操作、撤销/恢复、可访问性、移动端输入与布局、视觉一致性。
