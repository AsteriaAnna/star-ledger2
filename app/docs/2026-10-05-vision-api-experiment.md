# M5.1-O/F：截图识别 API 对照试验

状态：独立试验分支 `experiment/vision-api-20261005`。不改正式截图页面、账务规则、云函数或部署。已重新获取并基于 `origin/main` 提交 `63ab2e2`；15 张的正式 API 对照已运行，结果如下。

## 要回答的问题

1. 图像模型对实际截图读出哪些**可见事实**？金额、原单与部分退款、时间/状态、支付方式、长编号逐位准确率分别算。
2. 它提出哪些**资金事件候选**？把合计、页面提示、分类和退款详情里的原单号误当新交易，均算错误。账户余额、本人消费和最终入账仍由星账共享账务规则决定。
3. OCR 原文交给文本模型，与图像模型直读谁更稳定？现有 `parseScreenshot` 对相同 OCR 原文产生什么草稿？三者输入、输出分开记录，不混为一个“识别率”。
4. 同一张图先到、官方 Excel 后到，能否对齐来源身份且只产生一次账务效果？此项**尚无产品闭环实现**，模型 JSON 正确也不算通过。

## 试验入口与隐私

正式候选调用为腾讯云 TokenHub `POST /v1/chat/completions`，图片以 Base64 放在请求体中；密钥仅由运行环境的 `TOKENHUB_API_KEY` 提供，不进入网页、仓库、命令参数、报告或日志。脚本只允许三种已核实的模型 ID，不接受自定义目标地址。原图片留在用户提供的私密测试目录，脚本不复制、不主动删除；响应仅保存在被 `.gitignore` 排除的 `vision-api-results/`，文件权限 `0600`。不要将原图、OCR 全文、逐图结果或密钥推送 GitHub。

体验中心的对话框结果只作为模型行为线索，不能替代这个 API 调用，更不能替代星账手机端“截图分享/选择图片 → 等待 → 核对 → 入账 → 后续 Excel 合并”的验收。当前正式页面仍是本地 Tesseract 加单条 `parseScreenshot`，且其隐私文案写着图片不会上传；若以后接入云模型，必须同步更正事实披露。

图片暂存策略待产品实现：用户只截一次，处理期间复用同一私密副本；模型返回后由系统核验字段、事件和账务结果，失败/待核时允许重试，完成或明确放弃后清理**我们控制的临时图片**。原始用户照片及服务商按其协议可能留存的请求不在此删除承诺范围。测试脚本保留用户原图以便比较，不自动销毁测试素材。

## 运行

需要 Node 24+。脚本为 `app/scripts/benchmark-vision-api.mjs`；先用 `--dry-run` 检查选择，绝不调用模型：

```sh
node app/scripts/benchmark-vision-api.mjs --mode vision --input /PRIVATE/screenshots --out app/vision-api-results/pilot --select CASE_ID_1,CASE_ID_2 --limit 2 --dry-run
```

案例 ID 是脚本用图片**文件名**生成的 12 位摘要，不是图片内容指纹。运行时目录内保留原文件名。设置 `TOKENHUB_API_KEY` 后移除 `--dry-run`，每个选中图、每个模型最多一次请求；网络错误不自动重试，避免重复计费。

```sh
node app/scripts/benchmark-vision-api.mjs --mode vision --input /PRIVATE/screenshots --out app/vision-api-results/pilot --select CASE_ID_1,CASE_ID_2 --models hy-vision-2.0-instruct,hunyuan-t1-vision-20250916 --limit 2
node app/scripts/benchmark-vision-api.mjs --mode ocr-text --input /PRIVATE/screenshots --ocr-json /PRIVATE/ocr-results.json --out app/vision-api-results/ocr-text --select CASE_ID_1,CASE_ID_2 --models hy-vision-2.0-instruct --limit 2
node app/scripts/benchmark-vision-api.mjs --mode local --input /PRIVATE/screenshots --ocr-json /PRIVATE/ocr-results.json --out app/vision-api-results/local --limit 15
```

`--ocr-json` 为包含 `{file,text}` 的数组；`file` 与图名相同。输出每个调用的原始模型文字、可解析 JSON、finish reason、token 用量、耗时或错误码，**不含输入图片**。若输出被截断、不是 JSON、长编号不一致或状态含臆测，应按失败/待核记录，而非人工补成模型成功。模型请求输出上限固定为 1800 tokens；更改提示/额度要单独记录版本，不能与旧结果直接混算。

本执行环境中 Node 24 `fetch` 需要 `NODE_USE_ENV_PROXY=1` 才能通过已配置代理访问接口。第一次不带此选项的请求在 39 ms 返回 `NETWORK_ERROR`，无模型响应；随后开启代理的调用成功。运行环境若直连可用，不应机械套用此代理选项。

## 2026-10-05 正式 API 首轮结果

模型 `hy-vision-2.0-instruct`；同一套提示、温度 0、输出上限 1800。每张原图直读一次、先前 RapidOCR 原文作为文字输入一次，共 30 次成功响应，无自动重试。受限 Key 仅授权这一已启用模型，控制台其他两个候选显示未启用，因此**没有声称多模型 API 对比**。这些数字是小样本观测，不是未来生产准确率或价格承诺。

| 路径 | 有响应 | 严格 JSON 可解析 | 合计用量 | 平均耗时 | 长编号逐位正确（按私密真值 22 个字段） |
|---|---:|---:|---:|---:|---:|
| 原图 → HY-Vision 2.0 | 15/15 | 14/15 | 41,118 tokens | 10.9 秒 | 19/22 |
| RapidOCR 文字 → 同一模型 | 15/15 | 15/15 | 13,422 tokens | 8.9 秒 | 19/22 |

逐位核验：图像直读在 02 的断行转账号读出了最后一位，05 的断行商户单号也完整，但 05 商品说明内的另一个编号有错位；07 两个不同编号均多读了一位。文字输入在 02、05 的三个断行编号继承了 OCR 的截断，其余可见编号正确。09、15 本无长订单号，不应因未输出编号扣分或补造。15 图像输出含可读 JSON 后又附加模型标记，严格解析失败；不能人工截取前半段算作接口成功。15 的分钟时间还被写成 `12:11:00`，虽标注 minute 精度，却伪造秒值。

资金事件方面，原图输入正确读到 14 的原支付 79.59 及两笔退款 0.26、0.44，却将候选退款合并为 0.70 一笔；01 提现本金与服务费可见，候选却作普通付款 1501.50，还把主额描述为“合计到账”；03/04 从银行卡给微信零钱充值，被提议为单项收入；02 押金退回被提议为普通支付加退款；15 是本软件已有记录的截图，不能自动再入账。文字输入的 05 只提出退款 7.22、漏掉原支付 44，14 只提出合计退款 0.70、漏掉原支付及分笔退款。文字输入 01 还把历史节点“银行处理中”误当当前状态。09 亲情卡由他人代付但本人消费、11 校园充值作为消费等口径，也不能从通用模型事件标签直接得到余额和消费效果。

这轮确认了图像模型能补部分 OCR 断行，但会错读其他长号；文字模型节省调用量，却无法修复上游 OCR 遗漏，并可能进一步丢掉原支付。**两者都不具备直接写账资格**。本地 `parseScreenshot` 基线仍是一图一草稿，14 取 0.26 为主额、01 提现当消费等缺口没有因模型实验而改变。下一步应先设计共同的来源事实、每图多事件、关系证据和统一账务命令，再针对有证据的字段做受约束的 AI 辅助，逐例回归；不从这些响应直接落账。

私密逐图原文、令牌用量和现有解析器基线仅在忽略目录 `app/vision-api-results/`；原图与逐位真值不进公共仓库。实际生产端到端、Excel 后到去重、手机分享及不同模型尚未验收。试验 Key 应在本轮结束后停用，临时 Key 文件清理；原始用户测试素材按用户后续验收需要留存。
